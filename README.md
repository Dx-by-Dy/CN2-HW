# Потоковое видео через RTSP и RTP (Rust)

Решение задачи по программированию сокетов 6: сервер и клиент потокового видео.
Клиент управляет сеансом по RTSP (TCP), сервер передает кадры MJPEG в RTP-пакетах (UDP).
Исходный учебный код был на Python 2 и Tkinter, здесь он переписан на Rust.

Сделано:

- основное задание: RTSP на клиенте (SETUP, PLAY, PAUSE, TEARDOWN) и RTP-пакетирование на сервере;
- дополнительное задание 1: статистика сеанса в окне клиента (потери пакетов, скорость потока);
- дополнительное задание 2: плеер с тремя кнопками Play, Pause, Stop, без отдельной кнопки Setup;
- дополнительное задание 3: метод DESCRIBE, описание видео в формате SDP.

## Установка Rust

Нужен Rust **1.95 или новее**.

**Linux и macOS:**

```sh
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source "$HOME/.cargo/env"
rustc --version
```

**Windows:** скачайте и запустите `rustup-init.exe` с https://rustup.rs.
Для сборки нужны Visual Studio Build Tools с компонентом «Desktop development with C++».
Если их нет, установщик предложит их поставить.

Если Rust уже установлен, но версия старше 1.95, обновите его:

```sh
rustup update
```

Дополнительные системные пакеты для сборки обычно не нужны. Клиенту для работы нужен графический
рабочий стол (X11 или Wayland на Linux). Сервер работает и без графики.

## Сборка

```sh
cd VideoStreamingRust
cargo build --release
```

При первой сборке cargo скачает зависимости, нужен интернет.
Готовые программы появятся в `VideoStreamingRust/target/release/`:
`server` и `client` (на Windows `server.exe` и `client.exe`).

## Видеофайл

Видео `movie.Mjpeg` входит в материалы задания (`Socket6_VideoStreaming/VideoStreamingCode/movie.Mjpeg`)
и в репозиторий не добавлено.

Имя файла клиент передает серверу в запросе SETUP, а **сервер открывает его относительно
своей текущей папки**. Проще всего запускать сервер из папки, где лежит видео.

## Запуск

Сначала сервер, потом клиент.

```sh
server <порт_сервера>
client <адрес_сервера> <порт_сервера> <RTP_порт> <видеофайл>
```

- `порт_сервера` — TCP-порт для RTSP. Выбирайте номер больше 1024, например 8554.
- `RTP_порт` — UDP-порт на машине клиента, куда сервер будет слать видео, например 25000.
- `видеофайл` — путь к видео относительно папки сервера.

### На одной машине

```sh
cd Socket6_VideoStreaming/VideoStreamingCode
../../VideoStreamingRust/target/release/server 8554
```

Во втором терминале, из корня репозитория:

```sh
VideoStreamingRust/target/release/client 127.0.0.1 8554 25000 movie.Mjpeg
```

Вместо готовых программ можно запускать через cargo из папки `VideoStreamingRust`:

```sh
cargo run --release --bin server -- 8554
cargo run --release --bin client -- 127.0.0.1 8554 25000 ../Socket6_VideoStreaming/VideoStreamingCode/movie.Mjpeg
```

### На разных машинах

Сервер и клиент должны быть в одной локальной сети (или в одной VPN): сервер шлет видео
по UDP на адрес, с которого пришло RTSP-соединение, и через NAT эти пакеты не пройдут.

1. На сервере откройте TCP-порт сервера:
   - firewalld (Fedora): `sudo firewall-cmd --add-port=8554/tcp`
     (до перезагрузки; чтобы сохранить, повторите команду с `--permanent`);
   - ufw (Ubuntu): `sudo ufw allow 8554/tcp`.
2. На клиенте разрешите входящий UDP на RTP-порт:
   - firewalld: `sudo firewall-cmd --add-port=25000/udp`;
   - ufw: `sudo ufw allow 25000/udp`;
   - Windows сам спросит разрешение при первом запуске клиента.
3. Запустите клиент с адресом сервера в локальной сети:

   ```sh
   client 192.168.0.18 8554 25000 movie.Mjpeg
   ```

## Работа с клиентом

| Кнопка | Действие |
|--------|----------|
| Play   | без сеанса: подключиться к серверу (если еще нет), затем DESCRIBE, SETUP и PLAY; на паузе: PLAY (продолжить с того же места) |
| Pause  | приостановить воспроизведение (PAUSE) |
| Stop   | завершить сеанс (TEARDOWN); следующий Play начнет видео сначала |

Кнопки, недоступные в текущем состоянии, неактивны.

При запуске клиент к серверу не подключается: соединение устанавливается при первом нажатии
Play. Если сервер недоступен, появится предупреждение, и следующее нажатие Play попробует
подключиться снова.

Справа от видео две панели: описание видео (Media info, из ответа на DESCRIBE) и статистика.

Если закрыть окно, воспроизведение встанет на паузу и появится вопрос о выходе.
OK завершает сеанс и закрывает программу, Cancel продолжает воспроизведение.

Сервер и клиент пишут в терминал отправленные и полученные RTSP-сообщения и номера
принятых RTP-пакетов.

## Три кнопки вместо четырех (дополнительное задание 2)

**Когда отправляется SETUP.** При нажатии Play, если сеанса еще нет: при первом запуске
и после Stop (перед ним идет DESCRIBE, см. задание 3). PLAY нельзя отправить вместе с SETUP,
потому что в нем нужен номер сеанса из ответа на SETUP. Поэтому клиент ждет этот ответ и
сразу после него сам отправляет PLAY. Пока пользователь не нажал Play, сервер не держит
сеанс и открытый файл.

**Подходит ли TEARDOWN для Stop.** Да. Stop в плеере означает «остановить и вернуться в
начало». TEARDOWN завершает сеанс: сервер останавливает передачу и закрывает файл, а
следующий SETUP откроет его заново, с первого кадра. Перемотка через PAUSE потребовала бы
заголовка `Range` в PLAY, а сервер его не поддерживает.

TEARDOWN завершает RTSP-сеанс, но не TCP-соединение: новый сеанс идет по тому же соединению,
CSeq продолжает расти. Соединение закрывается только при выходе из программы.

Что делает клиент при новом сеансе:

- сбрасывает номер сеанса, номер последнего кадра и статистику: в новом сеансе кадры снова
  нумеруются с 1;
- оставляет RTP-сокет открытым до выхода и выбрасывает пакеты прошлого сеанса, оставшиеся
  в его буфере;
- не отправляет новый запрос, пока не пришел ответ на предыдущий, поэтому двойное нажатие
  кнопки не сбивает сеанс.

Сервер отвечает на каждый запрос, как требует задание: `200 OK` или код ошибки
(`404 Not Found` — нет файла, `455 Method Not Valid in This State` — команда недопустима
в текущем состоянии, `500 Internal Server Error`). Клиент показывает ошибку в диалоговом окне.

Повторный SETUP после TEARDOWN по тому же соединению работает только с сервером из этого
репозитория. Исходный сервер на Python после TEARDOWN не возвращается в INIT и новый SETUP
проигнорирует.

## Метод DESCRIBE (дополнительное задание 3)

DESCRIBE сообщает клиенту, что он будет получать, еще до создания сеанса. RTSP-заголовки
этого не дают (в них только CSeq, Session, Transport), а из RTP-пакетов можно узнать разве
что тип нагрузки, и то уже после начала передачи. По описанию клиент может заранее понять,
сумеет ли он проиграть поток, подготовить окно и показать длительность. А если файла нет,
ошибка видна сразу, до SETUP.

Клиент отправляет DESCRIBE при нажатии Play без сеанса, перед SETUP:

```
DESCRIBE movie.Mjpeg RTSP/1.0
CSeq: 1
Accept: application/sdp
```

Сервер отвечает описанием в формате SDP (Session Description Protocol, RFC 4566).
Ответ приходит до создания сеанса, поэтому заголовка Session в нем нет:

```
RTSP/1.0 200 OK
CSeq: 1
Content-Type: application/sdp
Content-Length: 177

v=0
o=- 0 0 IN IP4 127.0.0.1
s=movie.Mjpeg
t=0 0
a=range:npt=0-25.000          длительность, с
m=video 0 RTP/AVP 26           видео по RTP, тип нагрузки 26
b=AS:1365                      средний битрейт, кбит/с
a=rtpmap:26 JPEG/90000         кодек JPEG, частота RTP-часов 90 кГц
a=framerate:20                 кадров в секунду
a=x-dimensions:384,288         ширина и высота
a=x-frames:500                 число кадров
```

(Пояснения справа добавлены здесь для читателя, в настоящем ответе их нет.)

Сервер получает эти данные из файла: проходит по 5-байтным заголовкам кадров, не читая сами
кадры, а разрешение берет из маркера SOF первого JPEG-кадра. Частота кадров — это интервал
отправки сервера (50 мс). DESCRIBE допустим в любом состоянии и состояние не меняет.

Клиент показывает описание в панели Media info. В статистике строка Frame показывает номер
текущего кадра из общего числа (`123/500`). Когда приходит последний кадр, статистика
замирает: время после конца видео не уменьшает среднюю скорость, а текущая скорость не
падает до нуля.

**Метка времени RTP.** В SDP для JPEG указана частота RTP-часов 90 кГц, поэтому сервер ставит
в RTP-заголовок время кадра в видео в этих единицах. Каждый кадр добавляет 90000 / 20 = 4500
тактов, а начальное значение для каждого сеанса выбирается случайно (RFC 3550). Метка
отражает положение кадра в видео, а не момент отправки, поэтому после паузы она продолжается
без скачка. В исходном коде туда записывалось текущее время в секундах.

**Чтение сообщений из TCP.** Ответ с телом может прийти по TCP несколькими кусками, поэтому
сервер и клиент дочитывают тело до Content-Length. Сообщения без тела в учебном протоколе не
заканчиваются пустой строкой, и их по-прежнему считают пришедшими за одно чтение. Поэтому
начало сообщения до строки Content-Length должно прийти одним куском. Сообщения короткие и
отправляются одним вызовом, так что на практике это выполняется.

## Статистика (дополнительное задание 1)

Панель справа от видео обновляется несколько раз в секунду:

| Показатель        | Как считается |
|-------------------|---------------|
| Session state     | состояние сеанса: INIT, READY или PLAYING |
| Frame             | номер текущего кадра из общего числа кадров (из DESCRIBE) |
| Packets received  | сколько RTP-пакетов пришло |
| Packets lost      | по пропускам в номерах пакетов, как в RFC 3550: ожидалось `последний − первый + 1`, потеряно `ожидалось − принято`; в скобках доля потерь |
| Out of order      | пакеты, пришедшие позже пакета с бо́льшим номером |
| Bitrate           | скорость видеопотока за последнюю секунду, бит/с; на паузе падает до 0 |
| Average bitrate   | средняя скорость за все время воспроизведения, паузы не учитываются |
| Frames per second | кадров за последнюю секунду |
| Data received     | общий объем принятых видеоданных |

Скорость считается по видеоданным без 12-байтных RTP-заголовков. После Stop статистика
обнуляется: новый сеанс считается с нуля. На последнем кадре видео статистика замирает,
заголовок панели меняется на «Statistics (finished)».
Если потерялся сам последний пакет, клиент не узнает о конце видео, и статистика не замрет.
Если теряются последние пакеты перед паузой или остановкой, клиент этого не узнает:
пакета с бо́льшим номером уже не будет.

## Структура проекта

`VideoStreamingRust` — Cargo workspace из трех крейтов:

```
VideoStreamingRust/
├── common/src/            общее для клиента и сервера
│   ├── method.rs            Method: SETUP / PLAY / PAUSE / TEARDOWN
│   ├── state.rs             State: INIT / READY / PLAYING и переходы между ними
│   ├── rtsp_request.rs      RtspRequest: сборка и разбор RTSP-запроса
│   ├── rtsp_reply.rs        RtspReply: сборка и разбор RTSP-ответа
│   ├── media_info.rs        MediaInfo: описание видео и его запись/разбор в SDP
│   ├── read_message.rs      чтение одного RTSP-сообщения из TCP
│   ├── rtp_packet.rs        RtpPacket: кодирование и декодирование RTP-пакета
│   └── event.rs             Event: флаг остановки для потоков
├── server/src/
│   ├── main.rs              разбор аргументов
│   ├── server.rs            Server: прием TCP-подключений
│   ├── server_worker.rs     ServerWorker: RTSP-сеанс одного клиента
│   ├── rtp_sender.rs        RtpSender: отправка кадра каждые 50 мс
│   └── video_stream.rs      VideoStream: чтение кадров и описание файла MJPEG
└── client/src/
    ├── main.rs, config.rs   запуск и параметры командной строки
    ├── app.rs               ClientApp: окно, кнопки, диалоги, панели описания и статистики
    ├── rtsp_client.rs       RtspClient: RTSP-запросы и обработка ответов
    ├── rtp_receiver.rs      RtpReceiver: прием RTP и декодирование JPEG
    ├── session.rs           Session: CSeq, номер сеанса, состояние, ожидание ответа
    ├── stats.rs             Stats: статистика сеанса
    ├── ui_handle.rs         UiHandle: передача кадров и предупреждений в окно
    └── warning.rs           Warning: текст предупреждения
```

Соответствие исходным файлам на Python:

| Python              | Rust |
|---------------------|------|
| `Server.py`         | `server/src/main.rs`, `server/src/server.rs` |
| `ServerWorker.py`   | `server/src/server_worker.rs`, `server/src/rtp_sender.rs` |
| `VideoStream.py`    | `server/src/video_stream.rs` |
| `RtpPacket.py`      | `common/src/rtp_packet.rs` |
| `ClientLauncher.py` | `client/src/main.rs` |
| `Client.py`         | `client/src/app.rs`, `client/src/rtsp_client.rs`, `client/src/rtp_receiver.rs` |

Формат RTSP-сообщений совпадает с примером из задания.
